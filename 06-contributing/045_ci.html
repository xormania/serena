The CI Matrix#

Serena’s CI has a problem most projects never meet: sixty-odd languages, each with its own toolchain, and no runner that could hold them all at once. The answer is a matrix with opinions — and the opinions are written down, in the header of .github/workflows/pytest.yml. This page walks through them; when CI surprises you, that header is the primary source.

Five batches, three operating systems#

Tests run as parallel matrix jobs over (OS × batch). The five batches are marker-based — jvm, native, other-langs, niche, and a catch-all for everything unmarked — and the batching is deliberately by pytest marker, not pytest-xdist: tests share fixtures, language-server processes and on-disk resources, so in-process parallelism would race them.

Two properties keep the partition honest: each batch installs only the toolchains its languages need, and catch-all is defined as the negation of all the named groups — every test lands in exactly one batch, and adding a language cannot desync the split.

Where the matrix thins out#

The default is the full cross-product, with two kinds of exception:

  • niche runs on ubuntu only. Its toolchains (lean4, ocaml, nix, julia, R, perl) are heavy and slow — not worth the Windows and macOS cost.

  • An OS-specific language inside an all-OS batch (swift on macOS, haskell on Linux) is skipped one level down, by the central guard in test/conftest.py — never by the matrix.

That split matters when you add a language: OS gating belongs in the conftest, not in the workflow file.

Why a marker runs zero tests — or fails after the toolchain looked fine#

Whether a language’s tests run on a given machine is decided by more gates than “is the binary installed”, and every one of these was learned the hard way. The executable form of all of them is the doctor — uv run python scripts/check_dev_env.py mirrors the same rules the suite applies, and --markers prints the pytest -m expression your machine can actually run. The classes, with their sharpest examples:

  • Skips live in two places. The central guard in test/conftest.py (_determine_disabled_language_servers) is the taxonomy, but a few suites carry their own: the zig tests are class-level skipif’d on Windows inside their test file, and the clangd suite never consults the central guard at all. If -m <marker> collects zero tests, look in both places.

  • A guard can be narrower than the server it guards. The MATLAB guard accepts MATLAB_PATH or a handful of fixed macOS paths — a normal Windows or Linux installation skips silently, and setting MATLAB_PATH is the portable remedy. The Haskell guard wants haskell-language-server-wrapper on PATH, so a GHCup install works only once ~/.ghcup/bin is on your PATH.

  • Presence is not capability. Clojure needs the official CLI, not a distro launcher — both -Aaliases in its help and a working -Spath. C# needs a .NET SDK, not just the runtime: the test project is SDK-style, and a runtime alone cannot load it. Elixir needs mix (the fixture compiles with it), and Nix needs the nix CLI even when nixd is already on the PATH — the server refuses to start without it.

  • A missing binary does not mean a missing suite. Serena bundles or downloads its own runtimes for several languages — jdtls ships a JRE, and the Kotlin, Lua and Dart servers install themselves — but managed downloads have platform matrices: Dart’s SDK exists for win/mac x64+arm64 and linux x64 only, and the HLSL server is prebuilt for win x64/arm64 and linux x64, built via cargo on macOS, and unavailable elsewhere.

  • Discovery has an order. Nextflow resolves $JAVA_HOME/bin/java before the PATH (and the first hit must be JDK 17+); rust-analyzer is found via rustup, then the PATH, then common install locations like ~/.cargo/bin.

When the doctor and this page disagree, the doctor is generated from the code and wins.

The ceilings#

GitHub’s free tier caps runs at 20 concurrent jobs and 5 concurrent macOS jobs. The current matrix is 13 jobs, 4 of them macOS — inside both limits, and anything that adds batches or operating systems has to stay inside them too, or jobs queue. Superseded runs on the same ref are cancelled outright to free capacity, and every job carries a 60-minute timeout: a healthy warm-cache run peaks around 16 minutes, and the ceiling exists because a hung job once burned the full six hours.

Caching#

Language servers are cached per (OS × batch); the uv venv is keyed on uv.lock; several individual toolchains and the web fixtures’ npm state have caches of their own. Most of the niche toolchains restore from cache, which is why that batch stays fast despite its size.

What this means for your pull request#

  • poe lint and poe type-check run once per OS, in the catch-all batch — the format gate is the first thing to fail, in the first minute.

  • Your language’s tests run in whichever batch its marker belongs to; nothing to configure.

  • A red run is usually one red job. Read that job’s log before concluding anything about the other twelve — and note where in the job it died: a failure before “Test with pytest” is the environment, not your diff, and even mid-run reds can be environmental (ccls has been seen crashing during indexing; a rerun of the failed job cleared it).

  • The docs build (Sphinx, warnings as errors) and a spell check run alongside the tests.
